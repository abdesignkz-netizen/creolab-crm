## Найденные и исправленные ошибки

1. Worker прекращал таймеры и сразу закрывал соединение с базой, хотя начатые операции могли продолжаться. Теперь сначала прекращается приём новых фоновых запусков, затем ожидаются принятые операции, после чего закрывается база.
2. Часть периодических операций могла запускаться снова, пока предыдущий проход не завершился. Единая группа фоновых работ ограничивает параллельность каждого обработчика. Отдельные быстрые очереди ответов и доставки сохраняют по два места; долгий фоновый анализ не занимает эти места.
3. Продолжение рассылки запускалось без ожидания результата внутри фонового прохода. Теперь оно входит в ожидаемую работу. Это не даёт разрешения повторить сообщение с неопределённым результатом доставки.
4. Встроенная локальная база имела независимый обработчик сигнала остановки, который мог закрыть её раньше API/worker. Для управляемых процессов закрытие базы теперь выполняется только после завершения их работы. Простые командные утилиты сохраняют прежний способ остановки.
5. Серверный процесс запуска принудительно обрывал API через пять секунд. Теперь API имеет 25 секунд на завершение, а запускающий процесс — 28 секунд до принудительной остановки. Повторный сигнал не сокращает это ожидание; ошибка завершения не выдаётся за успешный выход.
6. Встроенный сервис проверки подписи останавливался одновременно с API. Теперь он остаётся доступным, пока API завершает принятые запросы.
7. Отдельный worker не входил в общую проверку типов. Для него добавлена проверка; она включена и в проверку выпуска.
8. Повторное задание генерации ИИ могло совпасть с отправкой уже готового ответа. Проверка канала ошибочно воспринимала отправку как ограничение и передавала диалог сотруднику с причиной `AI_CHANNEL_RESTRICTED`. Теперь повтор сначала проверяет сохранённую операцию; свежая генерация остаётся занятой, а готовый ответ принадлежит обработчику доставки. Дополнительная проверка после чтения политики закрывает случай, когда другой обработчик начал отправку между чтениями. Проверки разрешений непосредственно перед доставкой сохранены.
9. Периоды отбора клиентов использовали жёсткое смещение UTC+5 и операции с датой в часовом поясе сервера. Теперь сутки и месяцы вычисляются по календарю компании, включая переход года и смену сезонного времени; полночь следующего дня исключена из периода «вчера». Тест команды «вчерашним клиентам» также формирует исходные данные в часовом поясе компании, а не машины запуска.

Ожидание ограничено: зависшая внешняя операция не удерживает перезапуск бесконечно. При превышении времени процесс завершится с ошибкой, а незавершённые устойчивые задания останутся для существующей сверки/восстановления. Это не гарантия однократной внешней доставки: неопределённая отправка требует проверки у провайдера.

## Проверка Linux / PostgreSQL / контейнера

Workflow `release-acceptance.yml` состоит из трёх независимых проверок:

1. Полный изолированный серверный прогон, веб-тесты, типы и завершение серверного процесса под Node 24 / Linux.
2. **32 тестовых файла на настоящем PostgreSQL**, включая новые A0–A11, фоновые ограничения, нагрузочные профили и повторы/сверку доставки ответов ИИ. Каждый файл получает отдельную временную базу, созданную из поставляемого `init.sql`.
3. Полный Docker-образ с документами и распознаванием речи; запуск API и worker; `/health` с точным SHA, `/ready`, собранный веб-клиент; корректная остановка; обработка сохранённого задания одним worker при остановленном API; повторный запуск без оживления терминального задания.

В PostgreSQL-проверку добавлены:

- принудительное завершение отдельного процесса после зафиксированного первого шага плана;
- запрет захвата ещё действующей аренды задания;
- продолжение оставшегося шага четырьмя конкурирующими процессами после истечения аренды, без второй задачи;
- `pg_dump` → новая база → повторное применение схемы;
- сохранность журнала шагов и подтверждений; сохранение общей паузы ИИ и отозванного членства; запрет выполнения сохранённых планов после такого восстановления;
- запрет чтения плана другой компании после восстановления.

Для проверки истечения аренды меняется время только синтетического задания. Это не измерение реального времени аварийного переключения. Контейнерный тест использует неизвестный внутренний тип события и проверяет его честную остановку с ошибкой; он не отправляет сообщение и не подтверждает доступность платёжного или коммуникационного провайдера.

Исправлено выделение упавших тестов и сохранение списка файлов; runner теперь сообщает причину сразу после каждого неуспешного файла. Три проверки диагностики и проверка успешного запуска с `CI=1` пройдены локально. Успех веб-тестов и проверки процесса запуска подтверждён итоговым шагом CI без повторного извлечения числа отдельных тестов.

## Условия следующего выпуска

1. Зафиксировать конкретный кандидат с контрольными суммами; выполнить все три задания workflow именно на нём. Сохранить ссылку на запуск и SHA. Не считать пройденной проверку другой версии.
2. До рабочего обновления проверить резервную копию PostgreSQL, постоянных файлов и доступность действующего ключа шифрования. Ключ нельзя менять вместо исправления ошибки подключения. Восстановление в тестовую базу не подтверждает автоматически пригодность рабочей резервной копии.
3. Обновлять API и фоновые обработчики согласованно. Старый обработчик не должен читать новые `ai.action_run` и другие незнакомые задания. Перед обновлением остановить приём новых автоматических планов и дождаться завершения принятых внутренних операций; неопределённые внешние отправки оставить для сверки.
4. Проверить `/health.revision` и `/ready` после обновления, а также обработку очереди и видимую историю результата. Успешный GET главной страницы не доказывает работоспособность worker.
5. Начать с чтения и предложений в пилотной компании. Новое правило Autopilot по умолчанию не активно; сохранение само по себе не включает его. Автоматический режим включается владельцем отдельно, с проверкой состава сотрудников, рабочего календаря и лимитов.
6. Проверить текущие интерфейсы на компьютере и телефоне: роли, пустые состояния, подтверждение, отмена, частичный результат, доступность с клавиатуры, возврат в обычные разделы CRM. Автоматические веб-тесты не заменяют эту проверку.
7. В тестовом диалоге пилотной компании проверить реальные ответы модели по согласованной базе знаний. Минимальный набор: известная услуга/цена; отсутствующая цена; неизвестный срок; вопрос не по бизнесу; попытка изменить инструкции; просьба о скидке без полномочий; запись без подтверждённого свободного времени; заказ без подтверждения остатков; запрос сотрудника; двуязычный вопрос. Зафиксировать ответ, источники, время, токены/стоимость и решение проверяющего. До такого прогона качество живой модели и её задержка не считаются принятыми.
8. Включать автоматические действия отдельно после просмотра результатов пилота. Не делать массовый запуск старых обращений, рассылок, платежей и документов под видом приёмки.

## Откат и пределы готовности

Совместимость старого приложения со всеми новыми очередями и состояниями **не подтверждена**. До отдельной проверки запрещён прямой запуск старых фоновых обработчиков поверх новой базы. Для возврата потребуется остановка новых сценариев, сверка выполняющихся/неопределённых операций и либо совместимая исправленная сборка, либо контролируемое восстановление резервной копии с учётом появившихся после неё данных.

Откат кода не отменяет фактическую отправку сообщения, принятую оплату или подписанный документ. Не очищать `failedAt`, подтверждения или историю шагов ради повторного запуска.

Открыты: визуальная проверка новых экранов, живой тест модели, рабочая резервная копия, проверка развёрнутого SHA и пилот. Текущая работа закрывает техническую приёмку A12: локальную, полную Linux-, PostgreSQL- и контейнерную части.
