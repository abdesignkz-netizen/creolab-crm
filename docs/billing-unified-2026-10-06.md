# Единый Billing BasQar — реализация и запуск

Дата: 6 октября 2026. Изменения подготовлены в рабочей копии; production не изменялся. Реальных списаний не выполнялось.

## Реализовано

Единый заказ и журнал платежей для карты Freedom Pay, контролируемой оплаты Kaspi и банковского перевода. Подтверждение включает оплату, подписку, лимиты, документы, аудит и очередь уведомлений в одной транзакции. Добавлены клиентский checkout, история и административные разделы. Существующие тарифы, Free, индивидуальные предложения и прежние заявки сохранены.

## Архитектура

`Plan → TenantPlan → BillingOrder → BillingPayment → подтверждение → activateSubscription → BillingInvoice / история`.

- Tenant — компания, покупающая SaaS. CRM Company — её контрагент; второй слой компаний не создаётся.
- TenantPlan остаётся подпиской. Прайсинг, календарные периоды, лимиты, RBAC, PDFKit, почта, фоновые задания и аудит переиспользованы.
- `services/billing/ledger.ts` — общий платёжный цикл. `renewals.ts` — продление и завершение доступа. Провайдер изолирован интерфейсом `PaymentProvider`.
- Суммы пересчитывает backend. Заказ хранит снимок цены и дополнений. Поля существующего проекта `amountMinor` содержат **целые тенге**, не тиыны; существующие значения не конвертируются.
- Сохраняется текущий каталог BasQar. Цена 49 990 ₸ из задания — пример, не замена действующего прайса.
- Upgrade активируется после оплаты. Оплаченный downgrade запланирован на границу текущего периода, без prorating. Дополнения входят в снимок заказа и существующую модель прайсинга.
- Блокировка tenant, уникальные ключи платежей/периодов и транзакции защищают от параллельных запросов. Повтор callback не продлевает подписку повторно.
- Неопределённый результат запроса в банк остаётся PROCESSING: система не повторяет потенциальное списание вслепую.
- После неудачного автопродления: PAST_DUE → GRACE_PERIOD → SUSPENDED. Данные CRM не удаляются. Успешная оплата восстанавливает доступ. Отмена автопродления сохраняет оплаченный период.

## База данных

Миграция: `packages/db/prisma/migrations/20261006_unified_billing/migration.sql`.

Добавлены BillingOrder, BillingInvoice, PaymentWebhookEvent, BillingSequence; расширены BillingPayment и TenantPlan. Добавлены номера документов, даты/статусы, provider references, согласие на recurring, зашифрованный профиль, будущая смена тарифа, ключи идемпотентности и составные внешние ключи tenant. Уникальные индексы исключают две открытые попытки одного заказа, повтор provider transaction и повторное использование одной Kaspi-ссылки.

Runner `packages/db/src/billingMigration.ts` запускается при создании клиента БД после существующих совместимых патчей. SQL выполняется атомарно под advisory lock, версия и SHA-256 записываются в BasqarSchemaMigration. Повторный запуск пропускает применённую миграцию; изменение её checksum останавливает запуск. После первого production применения файл менять нельзя — требуется следующая миграция.

Миграция проверена на изолированной PGlite, включая повторное применение и сохранение старых данных. Production PostgreSQL и копия реальной базы здесь не проверялись.

## Frontend

- `/billing` — существующий каталог плюс подписка, история, документы, продление и выбор нового способа оплаты.
- `/billing/checkout/:orderId` — три карточки способов, согласие на recurring, реквизиты покупателя, PDF/email, статус из backend и результат оплаты.
- `/admin/billing` — платежи с фильтрами/страницами, подписки, счета, тарифы и реквизиты; старые заявки доступны отдельно.
- RU/KK/EN для нового клиентского интерфейса. Адаптивная сетка, состояния загрузки, пустых данных, ошибок и ожидания подтверждения.
- Технические provider IDs не выводятся клиенту. Закрытые счета нельзя повторно отправлять на оплату. Обрабатываемую карточную оплату нельзя отменить локально.
- Смена способа осуществляется перед новым платежом; автоматического списания по нажатию кнопки настройки нет. Незавершённый ручной заказ можно отменить и создать заново с другим способом. При PROCESSING сначала требуется сверка с банком.

## Freedom Pay

Реализованы подписанные запросы создания оплаты, recurring, статуса, отмены и возврата на уровне адаптера. Карточная активация происходит только по проверенному callback: merchant, режим test/live, tenant, заказ, платёж, сумма и KZT должны совпасть. Установлен одностадийный режим `pg_auto_clearing=1`. Ответы API/XML тоже проверяются, включая вложенные данные; размер и сложность XML ограничены. Запросы имеют timeout, редиректы API запрещены.

PAN/CVV/PIN не сохраняются. Recurring reference шифруется существующим ENCRYPTION_KEY; используется только после согласия клиента и успешного первого платежа. Отзыв согласия во время ожидающего callback не включает recurring обратно. При выключенном merchant recurring клиенту не предлагается согласие.

Проверка статуса в админке не превращает платёж в PAID. При потерянном callback нужно сверить платёж в кабинете Freedom Pay и запросить повтор подписанного уведомления. Нельзя вручную подтверждать карточные платежи через экран банковских переводов.

Нужны договор, merchant ID/secret, разрешённый одностадийный карточный flow и recurring, публичные HTTPS URL и приёмочные тесты с merchant. Их нет в этой рабочей среде; тесты адаптера используют подписанные fixtures/mock transport. Refund/cancel предусмотрены интерфейсом, но самостоятельный пользовательский процесс возвратов с согласованием и бухгалтерской сверкой в эту версию не включён.

Документация провайдера: [создание платежа](https://docs.freedompay.kz/api-11620859), [result callback](https://docs.freedompay.kz/result-notify-12007677e0), [статус](https://docs.freedompay.kz/status-11620963e0), [recurring](https://docs.freedompay.kz/reccuring-payment-21166426e0).

## Kaspi

Сейчас controlled flow: клиент создаёт отдельный PENDING платёж; администратор привязывает официальную HTTPS-ссылку Kaspi и reference именно к этому заказу. Клиент получает QR и кнопку открытия ссылки. После сверки поступления администратор вводит сумму, дату, reference/комментарий; сохраняются его ID и аудит, затем вызывается общее подтверждение.

Общий статический QR и выдуманный API не используются. Уникальность ссылки в БД не заменяет банковскую сверку: администратор обязан выдавать реальную индивидуальную ссылку и проверять сумму/заказ в Kaspi. Для автоматизации нужны официальный merchant-доступ, договор, документированный API/callback и схема проверки подписи. После их получения меняется адаптер, а не ядро подписок.

## Bank Transfer

Реквизиты покупателя берутся из существующего TenantLegalProfile. Реквизиты продавца задаются единожды в PlatformSetting `billing.seller`. PDF содержит номер, стороны, банковские данные, период, сумму, НДС из настроек и назначение платежа. Снимки реквизитов сохраняются в счёте, последующее редактирование настроек старые документы не меняет.

Администратор подтверждает фактическое поступление с суммой, датой и reference/комментарием. Одна транзакция обновляет Payment, Order, Invoice и TenantPlan. Повторное подтверждение не продлевает период. Email использует существующую очередь/Resend и отправляет защищённую ссылку на документ. PDF-счёт **не является фискальным чеком**. Юридические вопросы фискализации и кассы должны быть решены продавцом перед запуском.

## Environment variables

Все новые переменные перечислены в `.env.example`; реальные секреты в репозиторий не добавлены.

| Переменная | Значение / назначение |
|---|---|
| BILLING_PROVIDER | `none` по умолчанию; `freedompay` включает карту при наличии ключей |
| FREEDOM_PAY_MERCHANT_ID | ID merchant, только backend |
| FREEDOM_PAY_SECRET_KEY | Секрет merchant, только backend |
| FREEDOM_PAY_API_URL | `https://api.freedompay.kz`; другой host не разрешён |
| FREEDOM_PAY_TESTING_MODE | `1` — тест, `0` — live; безопасное значение по умолчанию 1 |
| FREEDOM_PAY_RECURRING_ENABLED | `0` по умолчанию; `1` после активации merchant recurring |
| BILLING_KASPI_MANUAL_ENABLED | `0` по умолчанию; `1` после подготовки контролируемого процесса |
| BILLING_GRACE_PERIOD_DAYS | 5 по умолчанию, диапазон 1–30 |

Переиспользуются APP_BASE_URL, API_BASE_URL, ENCRYPTION_KEY и параметры существующей почтовой инфраструктуры (RESEND_API_KEY и адрес отправителя). KZT фиксирован на сервере; новые переменные success/failure URL и валюты не вводятся. Callback строится из API_BASE_URL, возврат — APP_BASE_URL и конкретного заказа.

- `npm run lint` проходит, но workspace не содержат самостоятельных lint-скриптов: это не отдельный содержательный lint-аудит. Новые файлы отформатированы.
- Полный прогон: 121 из 127 тестовых файлов. Шесть ошибок отдельно воспроизведены на исходном HEAD: companyMembers, documentErrorPresentation, documentsFill, documentsPhase3, esfAvrPocGuards, esfNcaLayerClient. Они относятся к старым ожиданиям/импортам и Origin-проверкам, а не к Billing.
- PDF визуально проверен; клиентский мобильный checkout 390 px и административное подтверждение → ACTIVE проверены в изолированной локальной базе.

## Production checklist

- [ ] Подписать/проверить договор Freedom Pay, получить merchant ID и secret безопасным способом.
- [ ] Согласовать одностадийные карточные платежи, валюту KZT и разрешение recurring.
- [ ] Указать публичные HTTPS APP_BASE_URL/API_BASE_URL. Callback: `${API_BASE_URL}/api/v1/billing/providers/freedompay/webhook`, POST, без пользовательской авторизации.
- [ ] Заполнить реальные реквизиты продавца и НДС в админке. Проверить PDF с бухгалтерией; решить применимость ККМ/фискального чека.
- [ ] Подготовить Kaspi Pay и процедуру индивидуальных ссылок/сверки, затем включить controlled flow.
- [ ] Сохранить ENCRYPTION_KEY и резервную копию БД. Проверить восстановление копии; не менять ключ при релизе.
- [ ] На копии production PostgreSQL запустить новую версию с провайдерами выключенными. Runner сам применит SQL; проверить BasqarSchemaMigration и старые TenantPlan/BillingPayment. Не использовать `prisma db push` или baseline/reset на рабочей базе.
- [ ] Выполнить production миграцию в окно обслуживания: первый старт новой версии применяет её под lock. Убедиться, что SQL-файл включён в образ. При ошибке устранить причину; не редактировать checksum вручную.
- [ ] Проверить тестовую карту, отказ, дубли callback, неверную сумму, возврат до callback, два одновременных запроса, восстановление потерянного callback.
- [ ] Проверить тестовый recurring, отмену согласия, один заказ на период, grace/suspension и восстановление доступа.
- [ ] Проверить счёт, email, права менеджера/чужой компании, ручное подтверждение Kaspi и перевода.
- [ ] Включить live mode только после merchant-приёмки; выполнить согласованный контрольный платёж и сверку.
- [ ] Настроить мониторинг FAILED/PROCESSING, недоставленных уведомлений, jobs, доступности callback и БД; назначить ответственного за сверку.

### Неопределённый платёж и откат

Если PROCESSING завис: открыть платёж в админке, выполнить «Проверить в банке», сверить merchant reference в Freedom Pay. Не создавать новое списание и не удалять попытку из БД. Запросить повтор callback у провайдера. Успешное открытие return URL не доказывает оплату.

Перед откатом выключить новые попытки и recurring, сохранить приём callback до сверки всех открытых карточных платежей. Старый бинарник не содержит нового callback: простой откат во время платежей может оставить их неподтверждёнными. Миграция аддитивная; таблицы/поля и журналы при откате не удалять. Восстановление snapshot БД после реальных списаний требует предварительной банковской сверки.
