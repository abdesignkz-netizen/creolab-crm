# Точечные ТЗ: ситуация, управление, задачи

Дата: 6 сентября 2026  
Контекст: ядро CRM уже есть. WhatsApp-бот подключён мостом (`creolab-ai-manager.onrender.com`), но это не делает картину в кабинете правдивой.  
Цель этой волны: **один честный экран общей ситуации** и команды/задачи вокруг него, а не ещё три списка.

## Жёсткие ограничения (не нарушать)

1. Ядро CRM не зависит от WhatsApp и телефона как PK. Ситуация без бота должна жить.
2. Единственный sender — `whatsappService.js` бота. Кабинет не шлёт в Green API сам.
3. Команды кабинета и WhatsApp пишут в **один** `aiMode` лида (`SET_MODE` / `addManagerInstruction`).
4. Открытие карточки не забирает диалог у ИИ.
5. Не строить второй inbox «как в мессенджере». Inbox = работа, не лента чатов.
6. Пустой список ≠ «всё спокойно», если мост мёртв, синка не было или заявки без телефона висят.

---

## Диагноз: что сейчас врёт

| Экран | Что показывает | Почему это не ситуация |
|---|---|---|
| Сегодня | Счётчики + incomplete + заявки `new/accepted` | Нет диалогов human/paused, нет просроченных задач в ленте, кнопка «Открыть» ведёт в Управление оптом |
| Управление | Все открытые диалоги + все открытые задачи + 10 заявок | Свалка. Спокойный ИИ-чат рядом с горящим. Нет ранга, нет next action, нет владельца |
| Задачи | Ручное создание + open/done | Нет связи в UI с заявкой/диалогом/сделкой, нет `waiting`/`canceled`, нет дедупа с ситуацией |
| Статистика | Числа за день | Не отвечает «что делать сейчас» |
| Мост | Health + sync snapshot | После деплоя Render `leads.json` может быть пуст. Кабинет молча показывает тишину |

Автозадача `process_inquiry` уже создаётся при заявке (`dedupeKey=inquiry-process:{id}`). На Сегодня она **не попадает в ленту**, а в Управление дублирует заявку.

---

## Принцип продукта

**Ситуация — единица работы, не сущность склада.**

Одна строка = один человеческий шаг. Источники (заявка, диалог, задача, incomplete) могут быть связаны, но на доске не дублируются.

```
источник (inquiry / conversation / task / intake)
        ↓ правила дедупа + ранг + свежесть
   SituationItem (что, почему, что сделать, кому, до когда)
        ↓
   экран «Ситуация»  +  команда на той же строке
```

«Управление» — не второй список, а **действия** над строкой ситуации (и над диалогом, если он привязан).  
«Задачи» — реестр обязательств, в том числе тех, которых ещё нет в ситуации (без срока, низкий приоритет, сделанные).

# ТЗ-1. Модель ситуации (ядро)

### Зачем
Чтобы все экраны читали одно и то же, а не каждый свою выборку.

### Модель (вычисляемая, не новая «таблица чатов»)

`SituationItem`:

| Поле | Тип | Смысл |
|---|---|---|
| id | uuid ситуации (стабильный) | `{kind}:{entityId}` |
| kind | enum | см. ниже |
| entityId | uuid | id заявки / диалога / задачи / intake |
| title | string | человеку, не технический id |
| reason | string | почему это здесь **сейчас** |
| nextAction | enum | единственный рекомендуемый шаг |
| severity | `critical` \| `high` \| `normal` \| `low` | только для сортировки и цвета |
| ownerMembershipId | uuid? | кто должен сделать шаг |
| dueAt | datetime? | срок обязательства, если есть |
| ageMinutes | int | с момента, когда ситуация стала актуальной |
| freshness | `live` \| `synced` \| `stale` \| `unknown` | для строк с WhatsApp |
| links | object | `inquiryId`, `conversationId`, `taskId`, `contactId`, `dealId`, `sellerLeadId` |
| blocked | bool | нельзя закрыть без другого шага (нет телефона) |
| snoozedUntil | datetime? | скрыта до |

`kind`:

- `needs_phone` — IncompleteIntake `pending`
- `inquiry_new` — заявка `new` (ещё не принята)
- `inquiry_accepted` — принята, нет сделки / нет следующего шага
- `conversation_human` — диалог `mode=human`
- `conversation_paused` — `mode=paused`
- `conversation_attention` — `needsAttention=true` при режиме ИИ (бот эскалировал)
- `task_overdue` — задача `open` и `dueAt < now`
- `task_due_today` — задача `open` и срок сегодня, не просрочена
- `task_unassigned_hot` — открытая задача `priority=high` без владельца и без due (иначе она не видна)

Не являются ситуацией (не класть на доску):

- диалог `mode=ai` без `needsAttention`
- задача `open` без срока и без high, если по той же заявке уже есть `inquiry_*`
- задача `process_inquiry` если заявка уже в ситуации — **слить**: одна строка `inquiry_*` с `links.taskId`
- тестовые заявки (`test=true`)
- закрытые сделки / done-задачи / revoked intake

`nextAction` (закрытый список, не свободный текст):

- `complete_phone` — дописать телефон
- `accept_inquiry` — принять заявку
- `open_inquiry` — открыть и решить (принять / в сделку / отказ)
- `take_conversation` — забрать у ИИ (только если ещё ai+attention)
- `reply_human` — ответить клиенту (режим уже human)
- `return_to_ai` — вернуть ИИ
- `resume_paused` — снять паузу
- `complete_task` — закрыть обязательство
- `assign_owner` — назначить себя или коллегу
- `instruct_ai` — поручение, не забирая диалог

### Дедуп (обязательные правила)

1. Intake и заявка по одному событию не сосуществуют: intake `completed` исчезает.
2. `inquiry_*` + task `dedupeKey=inquiry-process:{inquiryId}` = **одна** строка kind=`inquiry_*`.
3. Диалог и задача «обработать этот чат» = одна строка kind=`conversation_*`, task в links.
4. Если заявка конвертирована в сделку и диалог в human — остаётся **диалог**, заявка с доски уходит (`status` не `new/accepted`).
5. Стабильный `id` не меняется при смене title.

### Ранг (сортировка ленты)

1. `blocked=true` (нет телефона)
2. `conversation_human` с самым старым ожиданием ответа клиента/менеджера
3. `conversation_attention`
4. `conversation_paused` старше SLA (по умолчанию 2 часа)
5. `task_overdue`
6. `inquiry_new`
7. `task_due_today` / `inquiry_accepted`
8. `task_unassigned_hot`

Внутри группы: старше выше. Owner = я не поднимает выше critical чужого, но фильтр «Мои» есть.

### Состояние «отложил»

Новая тонкая таблица `SituationSnooze`:

- `tenantId`, `itemId` (тот же `{kind}:{entityId}`), `until`, `byUserId`, `reason?`
- Срок истёк — строка снова в ленте.
- «Скрыть навсегда» запрещено для `needs_phone` и `inquiry_new`.

### API

`GET /api/v1/situation`

Query: `scope=all|mine`, `includeSnoozed=false`.

Ответ:

```json
{
  "asOf": "ISO",
  "freshness": {
    "seller": { "configured": true, "reachable": true, "lastSyncAt": "ISO|null", "leadCountOnBot": null },
    "warning": null
  },
  "metrics": {
    "now": 4,
    "blocked": 1,
    "needsHuman": 2,
    "overdue": 1,
    "mine": 2
  },
  "items": [ "SituationItem..." ]
}
```

`warning` обязателен, если:

- бот настроен и `reachable=false` → «Картина неполная: бот не отвечает»
- `reachable=true` и `lastSyncAt` пуст → «Диалоги WhatsApp ещё не забирали»
- `reachable=true` и lastSync старше 15 мин и есть sellerLead → «Синк устарел» (не блокирует работу с заявками)

`leadCountOnBot` — добавить в `GET /internal/crm/health` бота поле `leadCount` (число, без тел и текстов). Кабинет показывает «на боте N лидов / в CRM M диалогов».

### Проверка ТЗ-1

- [ ] Автотест: заявка создаёт inquiry+task, situation возвращает **1** item.
- [ ] Автотест: intake без телефона — kind=`needs_phone`, `blocked=true`, next=`complete_phone`.
- [ ] Автотест: диалог ai без attention отсутствует.
- [ ] Автотест: диалог human есть, ранг выше новой заявки того же возраста.
- [ ] Автотест: WhatsApp не настроен — situation всё равно отдаёт заявки, warning нет про бота.
- [ ] Автотест: бот настроен и unreachable — warning есть, заявки на месте.

# ТЗ-2. Экран общей ситуации (замена «Сегодня»)

### Зачем
Человек за 5 секунд видит: сколько горит, что делать первым, чего нельзя решить из-за дыр в данных.

### Состав экрана (один маршрут `/today`, заголовок «Ситуация»)

1. **Полоса свежести** (одна строка, не карточка метрик):
   - «Бот: отвечает / нет / не подключён»
   - «Синк: только что / 12 мин назад / не было»
   - Если warning — текст warning + кнопка «Забрать диалоги» или «К интеграциям»
2. **Четыре числа только из situation.metrics** (не из разрозненных count):
   - Сейчас (`now`)
   - Без телефона (`blocked`)
   - Нужен человек (`needsHuman`)
   - Просрочено (`overdue`)
   Число = длина соответствующих items, не отдельный «красивый» count. Расхождение запрещено.
3. **Лента** — строки ситуации по рангу.
   Каждая строка:
   - title
   - reason (почему сейчас)
   - nextAction человеческой фразой
   - owner или «без ответственного»
   - due / возраст
   - **одна** primary-кнопка = nextAction
   - secondary: открыть карточку источника
4. Фильтры: Все / Мои / Без ответственного. Не плодить вкладки по сущностям.
5. Пустые состояния (взаимоисключающие, по приоритету):
   1. Нет компании → войти заново
   2. Warning про бота + items пусты → «Заявки и задачи пусты, WhatsApp не подтянуть»
   3. Items пусты, бот не настроен → «Пока нет работы. Форма и задачи работают без WhatsApp»
   4. Items пусты, бот ок, синка не было → «В CRM пусто. Заберите диалоги или ждите заявку с сайта»
   5. Items пусты, синк был, на боте 0 лидов → «На боте нет сохранённых лидов (часто после рестарта Render без диска). WhatsApp у клиентов при этом может быть жив»
   6. Items пусты, на боте >0, в CRM 0 диалогов → ошибка синка, не «всё спокойно»

### Чего нет на этом экране

- Форма «новая заявка» (она на Заявках)
- Песочница ИИ
- Полный список всех диалогов в режиме ИИ
- Графики

### Проверка ТЗ-2

- [ ] Счётчик «Сейчас» = числу строк в ленте при фильтре Все без snooze.
- [ ] Primary на `needs_phone` открывает поле телефона, не Управление.
- [ ] Primary на `conversation_human` открывает диалог с фокусом на ответ, не забирает повторно.
- [ ] Mobile `/today` читает тот же `/api/v1/situation`.

# ТЗ-3. Управление = команда, не каталог

### Зачем
Сейчас Управление дублирует Сегодня и Диалоги. Нужен пульт над **текущей** ситуацией и живым диалогом.

### Что оставить / убрать

Убрать с `/control` бесконечные списки «все диалоги / все задачи / все заявки».

Оставить три блока:

1. **Пульт бота** (как сейчас health + sync) — коротко.
2. **Командная лента** = те же `situation.items`, где `kind` начинается с `conversation_` **или** nextAction из `{take_conversation, reply_human, return_to_ai, resume_paused, instruct_ai}`.
3. **Поручение ИИ** — поле на строке диалога с `sellerLeadId`. Без sellerLead — текст «сначала синк», не тихий fail.

### Команды (контракт)

Каждая команда: optimistic UI запрещён без ответа API. После успеха — перечитать situation, не `location.reload`.

| Команда | API | Эффект на боте | Эффект в CRM |
|---|---|---|---|
| Забрать себе | `POST /conversations/:id/take` | `SET_MODE HUMAN` если есть sellerLead | mode=human, owner=я, controlVersion++ |
| Пауза | `POST /conversations/:id/pause` | `SET_MODE PAUSED` | mode=paused |
| Вернуть ИИ | `POST /conversations/:id/return-to-ai` | `SET_MODE AUTO` | mode=ai, needsAttention=false |
| Поручить | `POST /conversations/:id/instruction` | `ADD_INSTRUCTION` | Note internal + situation reason не меняется |
| Ответить | `POST /conversations/:id/messages` | send через бота | только если mode=human |

Правила:

- Take не вызывается повторно, если уже human и owner = я. Кнопка тогда «Ответить».
- Открытие `/conversations/:id` **не** делает take.
- Если бот unreachable — команда пишет в CRM и ставит `freshness=stale` + ошибка «на боте не применилось». Режим в CRM не притворяется синхронным успехом.
- Аудит: `auditEvent` на каждую команду (уже частично есть — довести до take/pause/return/instruction).

### Проверка ТЗ-3

- [ ] Take дважды подряд не плодит два SET_MODE без нужды (идемпотентность по controlVersion).
- [ ] Бот down: take возвращает 200/202 с `appliedOnSeller: false`, situation показывает stale.
- [ ] Поручение без sellerLead — 422 с понятным текстом, не 500.

# ТЗ-4. Задачи как обязательства

### Зачем
Задача — «я обещал сделать X к сроку», не дубль заявки.

### Жизненный цикл

`open` → `waiting` (ждём клиента/оплату) → `open`  
`open` → `done`  
`open` → `canceled`  
`waiting` не занимает слот «Сейчас», если нет `dueAt < now`. Просроченный `waiting` возвращается в ситуацию как `task_overdue`.

### Поля в UI (создание и карточка)

Обязательные: type, title.  
Сильные: dueAt, owner, priority, связь (inquiry / conversation / deal / contact).  
`conversationId` уже в схеме Task — добавить в `createTaskSchema` и форму.

Типы оставить закрытыми: `process_inquiry`, `call`, `proposal`, `payment`, `other`. Не давать свободную строку в UI.

### Правила автосоздания (уже есть — зафиксировать)

| Событие | Задача | dedupeKey | Попадает в ситуацию? |
|---|---|---|---|
| inquiry created | process_inquiry | `inquiry-process:{id}` | нет отдельно, слита в inquiry_* |
| intake pending | нет задачи | — | kind=needs_phone |
| conversation → human | нет автозадачи | — | kind=conversation_human |
| сделка без следующего шага | не создавать в этой волне | — | — |

Запрещено: крона, которая плодит follow-up «на всякий случай». Follow-up выключен (план этап 7).

### Реестр `/tasks`

- Фильтры: открытые / жду / все / просроченные / мои
- Группировка по due: просрочено, сегодня, позже, без срока
- Строка показывает родителя: «Заявка …» / «Диалог …» / «Сделка …»
- «Сделано» снимает с ситуации мгновенно
- Нельзя done для `process_inquiry`, пока заявка `new` — сначала принять или отклонить заявку (иначе ситуация и задача расходятся)

### Проверка ТЗ-4

- [ ] Вторая заявка с тем же id не создаёт вторую process-задачу (уникальный dedupeKey).
- [ ] Done process_inquiry при status=new → 422.
- [ ] Задача без due и не high не появляется в situation, видна в /tasks.
- [ ] Просроченная waiting снова в situation.

# ТЗ-5. Правдивые метрики

### Зачем
Числа не имеют права жить своей жизнью.

### Правила

1. Любой счётчик на Ситуации = `COUNT` тех же items, что в ленте.
2. `needsHuman` = items с kind `conversation_human|conversation_attention|conversation_paused`.
3. Статистика (`/stats`) не подменяет ситуацию. На статистике: заявки за день, конверсия, оплаты. Не «нужен человек» как второй источник правды.
4. Если синк вернул `total=0` при `reachable=true`, не писать «диалогов нет» без уточнения «на боте 0 лидов».

### Проверка ТЗ-5

- [ ] Тест: 2 human + 1 overdue + 1 intake → metrics.now=4, needsHuman=2, overdue=1, blocked=1.

# ТЗ-6. Свежесть WhatsApp (не новый sender)

### Зачем
Пустая CRM после рестарта Render не должна выглядеть как «продаж нет».

### Сделать

1. На боте в `/internal/crm/health` добавить `leadCount` и `storePathKind` (`persistent` если `DATA_DIR` задан, иначе `ephemeral`). Без содержимого чатов.
2. CRM после connect/health показывает: «На боте N лидов · в CRM M диалогов».
3. Sync пишет `integration.lastEventAt`. Situation freshness читает его.
4. Кнопка «Забрать» на Ситуации, если `M < N` или lastSync пуст.
5. Документ в Integrations: диск Render `/var/data` + `DATA_DIR` обязателен для живой истории. Это эксплуатация, не фича кабинета.

Не делать в этой волне: выгрузка истории из Green API, второй webhook на CRM.

### Проверка ТЗ-6

- [ ] Health без секрета по-прежнему 401.
- [ ] Health с секретом не содержит телефонов и текстов.
- [ ] Кабинет при N>0 и M=0 не показывает empty «диалогов нет» без warning.

# ТЗ-7. Mobile и уведомления (тот же контракт)

### Зачем
Иначе «общая ситуация» разъедется на третий список.

- Mobile Сегодня = `GET /situation` + те же primary actions (accept / complete phone / complete task / take).
- Не рисовать отдельную бизнес-логику в приложении.
- Уведомление `inquiry.created` и `conversation.needs_human` ведут в ситуацию, не в пустой inbox.
- Telegram сотрудника — следующая волна; не блокирует ТЗ-1…5.
