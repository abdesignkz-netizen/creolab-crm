# Подписание договоров на Render

## Причина ошибки 23 сентября 2026

Для `crm.creolab.kz` владелец подтвердил отсутствие `KALKAN_VERIFY_URL` в Environment. API в этом случае возвращает `gost_kalkan_adapter_missing`, а раньше интерфейс показывал общее «Проверка ЭЦП недоступна или не завершена». Запущенный на Mac Kalkan не обслуживает CRM на Render.

Предыдущий Dockerfile не устанавливал Java, не компилировал VerifyServer и запускал только Node API. Поэтому одного добавления URL недостаточно: на Render должен работать проверяющий сервис.

## Что изменено

- Dockerfile устанавливает Java и компилирует VerifyServer при сборке; стартует `scripts/start-api-with-kalkan.mjs`.
- Если официальный SDK установлен в `KALKAN_LIB_DIR`, запускатель поднимает Kalkan на `127.0.0.1`, ждёт загрузки SDK и доверенных УЦ, затем запускает API с локальным URL проверки.
- Явно заданный внешний `KALKAN_VERIFY_URL` сохраняется; локальный процесс в этом случае не запускается.
- Если библиотеки ещё не установлены и URL не задан, CRM продолжает работать, а подписание возвращает объяснение отсутствующей настройки. Если локальный URL задан явно, но SDK отсутствует, запуск завершается ошибкой, которую видно в журнале.
- Завершение одного из обязательных процессов останавливает второй. SIGTERM при перезапуске передаётся обоим процессам.
- Причины отказа подключения и проверки цепочки не теряются. В журнал не записываются договор, CMS, сертификат, БИН/ИИН или ключ пользователя.

Подпись принимается только при `cryptoStatus=VERIFIED` и `authorityStatus=VALID`. Установка SDK и успешный `/health` проверяют готовность процесса, но не подтверждают доступность внешнего OCSP/CRL или действительность конкретного сертификата.

## Применение к существующему сервису

1. Опубликовать изменения исходников в ветке, из которой собирается `creolab-crm`, и развернуть обновлённый Dockerfile `apps/api/Dockerfile` с контекстом корня репозитория. Убрать старое переопределение Docker Command, если оно обходит CMD образа. Сохранить существующие БД, диск и домен; seed не запускать.
2. На постоянном диске `/var/data` создать `/var/data/kalkan`. Загрузить туда официальные библиотеки SDK НУЦ. Локально для этой задачи подготовлен `basqar-kalkan-sdk-lib.tar.gz`: только JAR из установленного SDK, без пользовательских сертификатов, закрытых ключей и паролей. SDK не добавлен в Git. Передача на диск через SSH/SCP описана в [документации Render](https://render.com/docs/disks#transferring-files).
3. Распаковать архив так, чтобы JAR лежали прямо в `/var/data/kalkan/lib`, а не во вложенном дополнительном каталоге. В архиве уже есть каталог `lib`:

   ```sh
   mkdir -p /var/data/kalkan
   tar -xzf /var/data/basqar-kalkan-sdk-lib.tar.gz -C /var/data/kalkan
   ```

4. **После загрузки библиотек и обновления образа** сохранить в Render → Environment:

   ```text
   KALKAN_LIB_DIR=/var/data/kalkan/lib
   KALKAN_VERIFY_URL=http://127.0.0.1:4170
   KALKAN_VERIFY_PORT=4170
   KALKAN_OCSP=1
   KALKAN_VERIFY_TIMEOUT_MS=15000
   ```

   Порт 4170 наружу не публикуется. `127.0.0.1` относится к контейнеру Render. Локальные пути Mac на Render не работают. Для существующего внешнего Kalkan эти значения не применять: нужны его адрес и согласованный секрет.

5. Выполнить перезапуск/Deploy. В Logs должны появиться `Kalkan CMS verify ... ocsp=on`, `[kalkan] SDK ready; certificate revocation checks enabled`, затем запуск API. Проверить публичные `/health` и `/ready` CRM.
6. В Render Shell проверить внутреннюю готовность без отправки договора:

   ```sh
   node -e 'fetch("http://127.0.0.1:4170/health").then(async r => { console.log(r.status, await r.text()); if (!r.ok) process.exitCode=1; }).catch(() => { console.error("Kalkan недоступен"); process.exitCode=1; })'
   ```

7. Владелец повторно подписывает договор через свой NCALayer. Только эта проверка на рабочем сайте подтвердит весь путь с настоящим сертификатом. При отказе в Logs API будет безопасный код причины: `kalkan_unreachable`, `kalkan_timeout`, `issuer_cert_not_found`, `ocsp_unreachable` и т. п.

Внешние адреса НУЦ для проверки отзыва должны быть доступны с Render. При `UNCHECKED` проверку не отключать; установить причину по коду, актуальности SDK/УЦ и доступности OCSP/CRL.

## Проверки исправления

- `node --test scripts/start-api-with-kalkan.test.mjs`: внешний URL сохраняется, отсутствие SDK обрабатывается явно, неудачный запуск Java не запускает API.
- `cmsInspect.test.ts`: реальные CMS тестового сертификата, отказы проверки цепочки, отозванный сертификат, HTTP-ошибки сервиса, несовпадение подписанта и документа.
- `documentsPhase3.test.ts`: отсутствие настройки возвращает 503 с точной причиной; договор и запрос не становятся подписанными; проверенные стороны подписывают одну версию по очереди.
- Скомпилированный VerifyServer с установленным SDK: RSA и ГОСТ-2015; исходные байты принимаются, изменённый файл и attached CMS отклоняются.
- Совместный запуск с настоящим SDK на отдельном тестовом порту, готовность `/health`, отказ доверия синтетическому сертификату и завершение обоих дочерних процессов проверены отдельно.

Docker целиком локально не собирался: Docker в окружении отсутствует. Сборка образа и реальная подпись на Render требуют применения изменений к рабочему сервису. Самостоятельно в Render изменения в ходе подготовки не вносились.
