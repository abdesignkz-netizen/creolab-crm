# Защита BasQar: изменения и готовность к развёртыванию

Дата: 4 октября 2026 года. Проверена локальная рабочая копия. Изменения не развёрнуты на bsqr.kz. Настройки действующего хостинга, данные клиентов и реальные интеграции не изменялись. Это проверка кода и локальные тесты, а не независимый пентест или подтверждение полной защищённости.

## Что исправлено

| Риск | Изменение |
| --- | --- |
| Запросы на изменение данных со сторонних сайтов, в том числе соседних поддоменов | Проверка точного Origin/Referer и Fetch Metadata на изменяющих `/api/` запросах. Не используется доверие к Host или совпадению суффикса домена. Серверные интеграции и мобильные клиенты сохраняют собственную аутентификацию. |
| Кэширование персональных данных и раскрытие адресов публичных ссылок | `private, no-store` для API и публичных документов; `no-referrer`; запрет индексации. Уже скачанные пользователем копии эти заголовки не удаляют. |
| Выполнение внедрённых скриптов и встраивание приложения на чужом сайте | Content Security Policy ограничивает источники скриптов; запрещены inline-скрипты и обычный eval, внешние базовые URL и встраивание страниц. Сохранены PDF worker, WebAssembly и подключение NCALayer. Это дополнительный слой, не замена экранированию данных. |
| Чтение/запись за пределами файлового хранилища | Проверяются нормализованный путь и существующие символьные ссылки. Старые абсолютные ключи разрешены только внутри текущего хранилища. |
| Доступ к внутренней сети через URL вложения | Только HTTPS и стандартный порт; запрещены встроенные пароли, локальные, частные, служебные и переходные IP. Проверяются все DNS-ответы; разрешённый адрес закрепляется за соединением. Каждый редирект проверяется заново. Поток обрывается при превышении 16 МБ; общий сигнал таймаута — 20 секунд. |
| Рост памяти таблицы ограничений запросов | Не более 20 000 записей, периодическая очистка, активные ограничения не вытесняются новыми ключами. При заполнении новые ключи отклоняются. |
| Анонимные большие загрузки | Перед разбором больших JSON-загрузок CRM проверяется авторизация. Публичное подписание и подписанные события интеграций сохраняют свои механизмы проверки. Ошибки формата/размера возвращают безопасные 400/413. |
| Повышение прав при перезапуске | Bootstrap больше не назначает администратора существующему обычному пользователю по email, не восстанавливает заблокированного администратора и не сбрасывает его пароль. Нет email администратора по умолчанию. |
| Слабые ключи и отключённая TLS-проверка | API и worker в production отказываются запускаться с отсутствующими/явно слабыми/совпадающими ключами, включённой отладкой IP или отключённой проверкой TLS. Новые файлы создаются с ограничивающей umask. |
| Секреты в исключениях | Обработчик HTTP-ошибок и фоновые задачи в production больше не печатают произвольный текст и stack исключений провайдеров/БД. Сохраняется идентификатор запроса или название фоновой операции. Полный аудит всех журналов и сохраняемых в БД сообщений остаётся отдельной задачей. |
| Медленные HTTP-клиенты | Ограничено время получения заголовков/запроса, время простоя и число запросов на соединении. Это не защита от распределённой перегрузки. |
| Открытые инфраструктурные порты | В предоставленном `docker-compose.yml` PostgreSQL, Redis и API привязаны к `127.0.0.1`. Межконтейнерная связь сохраняется. Публичный доступ к API должен идти через HTTPS reverse proxy. |
| Уязвимые библиотеки | SheetJS обновлён с 0.18.5 до 0.20.3 из официального источника с закреплённой целостностью в lockfile; сохранены XLS/XLSX. Обновлены совместимые версии brace-expansion. |

Подход к защите запросов и загрузок опирается на [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) и [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). Источник обновления Excel — [официальная инструкция SheetJS](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/).

## Проверки

141 проверка API в 16 выбранных файлах прошла: вход/сессии, смена пароля, регистрация, администратор, разграничение компаний, файлы, подписи двух сторон, WhatsApp QR/Meta, публичные интеграции, импорт PDF/Excel и фоновые задачи. Проверки SSRF включают подменённые DNS-ответы, закрепление IP, редирект на служебный адрес и превышение размера потока. Использовались временные базы и отключённые внешние провайдеры.

Прошли 19 веб-тестов, проверка типов API/web/contracts, сборка web и `git diff --check`. Сборка предупреждает о размере отдельных JS-файлов. Проверка настроек запуска прошла на синтетических ключах; ключи рабочего сервера не проверялись.

Для повторения:

```sh
node scripts/test-api.mjs securityHardening securityMedia securityAuth securityTenant storage platformAdmin selfRegistration passwordReset contact avrSigning whatsappConnections metaConnections sellerConnection backgroundReliability integrationsFoundation manualPdfImport
npm run test --workspace @creolab/web
npm run typecheck --workspace @creolab/api --workspace @creolab/web --workspace @creolab/contracts
npm run build --workspace @creolab/web
```

Визуальная проверка в браузере не выполнена: среда Browser завершалась при запуске с ошибкой sandbox `TIOCSTI`. Перед публикацией проверить вход, загрузку PDF, резервный просмотр PDF и NCALayer в реальном браузере с включённой CSP. Реальная ЭЦП и отправка сообщений клиентам в этом аудите не выполнялись.

## Незакрытые предупреждения зависимостей

Аудит серверных и веб-workspace с `--omit=dev` после обновлений сообщает **6 записей: 4 high, 2 moderate, 0 critical**. Записи включают родительские пакеты и не означают шесть независимых уязвимостей:

| Цепочка | Оценка и оставшаяся работа |
| --- | --- |
| `node-forge` | [Предупреждение о проверке RSA PKCS#1](https://github.com/advisories/GHSA-86w9-cpqp-85rv), исправленная версия в аудите не предложена. В изученном коде BasQar forge разбирает ASN.1 и метаданные; решение о корректности реальной подписи принимает Kalkan. Нельзя считать весь пакет безопасным: требуется отслеживать исправление и отдельно перепроверять пути проверки подписей. |
| `prisma → @prisma/config → deepmerge-ts` | Три high-записи одной цепочки. Prisma CLI объявлен devDependency, но также попадает в граф зависимостей через peer-связи. Проблема связана с рекурсивным объединением объектов. Автоматический аудит предлагает смену версии Prisma; принудительное изменение поколения ORM не выполнялось. Нужно отдельно проверить фактический состав production-образа и совместимость исправленного CLI. |
| `exceljs → uuid` | Две moderate-записи одной цепочки. Найденное использование в ExcelJS — генерация v4; предупреждение касается буферов в v3/v5/v6. Это ограничивает применимость найденного пути, но не снимает предупреждение. Нужна совместимая замена транзитивной версии с проверкой экспорта. |

В общем монорепозитории остаются дополнительные предупреждения инструментов Expo/React Native и мобильной сборки. Полное обновление мобильного стека здесь не выполнено. Не использовать `npm audit fix --force` без отдельной проверки совместимости.

## Условия безопасного развёртывания

1. Выполнить `npm run security:check` **в окружении будущего production-сервера**, не передавая секреты в чат или аргументы команд. Нужны разные случайные `SESSION_SECRET`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `ENCRYPTION_KEY`, точные HTTPS-origin, адреса приложения/API и постоянный `STORAGE_DIR`.
2. **Не заменять ENCRYPTION_KEY вслепую:** старые зашифрованные ключи интеграций и сессии WhatsApp станут нечитаемыми. При недостаточной длине существующего ключа нужен отдельный перенос с расшифровкой старым ключом, повторным шифрованием новым и проверенной резервной копией. Смена ключей сессий/JWT завершит действующие входы.
3. Bootstrap создаёт только нового администратора при явно заданных email и пароле длиной от 12 символов. После первичной настройки удалить `PLATFORM_ADMIN_PASSWORD` из окружения. Существующие права и пароли управляются через авторизованные процедуры; конфликт email обычного пользователя блокирует bootstrap.
4. Проверить HTTPS reverse proxy, реальное число доверенных прокси и невозможность прямого обхода proxy к API. Не включать `TRUST_PROXY_DEBUG`. Ограничивать частоту и размер запросов на входном proxy, в том числе публичных загрузок и callback. Текущий limiter приложения локален процессу; для нескольких экземпляров нужен общий limiter/защита на входе.
5. Не использовать пример Docker Compose как готовую production-конфигурацию: в нём остаются демонстрационные пароли БД. На сервере задать отдельного пользователя БД с минимальными правами, закрыть PostgreSQL/Redis/Kalkan от интернета, ограничить административный SSH доверенными адресами, использовать ключи и отдельные учётные записи. Проверить ограничения исходящей сети, включая DNS.
6. Запускать API, worker и конвертеры с минимальными правами; текущие Dockerfile ещё требуют перехода с root с проверкой владельцев постоянного диска и доступа LibreOffice/Kalkan. Изолировать обработку документов и ограничить память, CPU, процессы и время. Новая umask не исправляет разрешения ранее созданных файлов.
7. Проверить шифрование дисков и резервных копий, отдельное хранение ключей, автоматические копии БД/файлов и восстановление на чистом окружении. Сохранить доказательство восстановления. Эти настройки на Render/PS.kz в текущей работе не проверены и не включены.
8. Внедрить обязательный второй фактор для администраторов BasQar; сейчас он не добавлен. Включить MFA для хостинга, домена, репозитория и почты восстановления. Проверить текущий список администраторов и отозвать лишние доступы и старые сессии.
9. Настроить наблюдение за входами, массовыми выгрузками, ошибками доступа, изменениями ролей и отказами резервирования. Ограничить доступ/срок хранения журналов. Отдельно проверить хранимые сообщения ошибок провайдеров на секреты и ПД; один HTTP-логгер не закрывает все каналы утечки.
10. После развёртывания выполнить внешнюю проверку открытых портов и заголовков, браузерные сценарии и независимый пентест. Только после этого фиксировать фактическую готовность рабочего сервиса. Поле юридической готовности `release.securityReviewed` этим аудитом не переключалось.

Владелец подтвердил: сейчас рабочий сервис находится на Render; перенос на PS.kz запланирован. Административный доступ к хостингу не предоставлен. До проверки на сервере перечисленные серверные меры не отмечаются выполненными.

## Render сейчас и перенос на PS.kz

В репозитории Render Blueprint описывает web-сервис с постоянным диском `/var/data`. Он не описывает отдельную БД и не подтверждает действующие настройки Dashboard. Изменение `docker-compose.yml` само по себе не закрывает порты на Render.

- Если используется Render Postgres, проверить, что API соединяется по internal URL, а внешний доступ к БД отключён либо ограничен точными доверенными IP. Сначала убедиться, что это не оборвёт действующие административные подключения и резервирование. У Render внешние IP-правила и внутренние подключения настраиваются отдельно. [Документация подключения](https://render.com/docs/postgresql-creating-connecting).
- Проверить резервирование именно используемой БД: для Render Postgres — доступные функции восстановления и экспорт логической копии; для PGlite/другой БД на диске — согласованный экспорт средствами БД. Снимок постоянного диска не считать единственной проверенной копией БД. [Копии Postgres](https://render.com/docs/postgresql-backups), [ограничения восстановления дисков](https://render.com/docs/disks).
- Перед переносом сделать проверенную копию БД, файлов и используемого ENCRYPTION_KEY с отдельным защищённым хранением. Восстановить на закрытом PS.kz-окружении и проверить вход, документы, роли и расшифровку интеграций. Временные учётные данные для переноса должны иметь срок действия и минимальные права.
- Не запускать одновременно активные QR-сессии, отправку сообщений, фоновые задания и планировщики на старом и новом сервере. Переключать после проверки копии и согласованной остановки записи; проверить TLS, разрешённые origin, callback/webhook адреса и IP, затем возобновлять обработку.
- После подтверждённого переключения отозвать временные доступы, проверить отсутствие доступной старой копии и действовать по установленному сроку хранения резервных копий. Не удалять единственную проверенную копию до завершения проверки переноса.
