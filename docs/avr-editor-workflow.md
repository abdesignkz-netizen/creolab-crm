# Создание АВР из сделки

В существующей вкладке «Документы → АВР» кнопка «Создать АВР» открывает
`/documents/avr/new`. Сначала выбирается сделка, затем редактируется АВР.
Сохранение черновика не обращается к NCALayer.
Во вкладке «ЭСФ» кнопка «Создать ЭСФ» открывает выбор сделки внутри
той же карточки и создаёт черновик существующим API. Отдельной вкладки
«АВР и ЭСФ» и общей кнопки создания нет.

## Данные и готовность

Готовность вычисляется из реквизитов, суммы, позиций/предмета сделки,
оплаты/завершения и существующих электронных документов. Учитываются
`paymentStatus`, `fulfillmentStatus`, `outcome` и `DealStage.isTerminal`,
без привязки к ID стадии. Закрытые документами сделки исключаются.
Номер сделки в интерфейсе — короткий существующий ID, отдельная нумерация
сделок не вводится.

Позиции берутся из сделки. Если их нет, используется предмет сделки,
количество 1 и общая сумма. Правки АВР сохраняются в существующем
`ElectronicDocument.sourceDataJson` с `editorVersion: 1` и переживают
повторную проверку. Позиции самой сделки не перезаписываются.

Изменение заказчика сохраняет основную Company; при отсутствии компании
используются существующие создание компании и привязка к сделке.
Исполнитель берётся из существующих реквизитов организации с прежним
механизмом дополнения из подтверждённого импорта договора. Основание
действия руководителя хранится в `Tenant.settingsJson.documents.directorBasis`
и доступно через прежний API реквизитов. Миграция базы не требуется.

Денежные расчёты выполняются целыми числами: количество в тысячных,
цена в сотых, ставка НДС в базисных пунктах. Округление до сотых выполняется
для каждой позиции, затем суммы складываются. Введены ограничения точности
и размера суммы. Хранение итогов остаётся в существующих Decimal-полях.

Неподписанный/отсутствующий договор остаётся предупреждением.
Счёт на оплату не требуется для АВР и ЭСФ.

## Сохранение и отправка

Добавлены только отсутствовавшие операции:

- `GET /api/v1/documents/avr/eligible-deals`
- `GET /api/v1/deals/:id/avr-context`
- `PATCH /api/v1/electronic-documents/:id` — редактирование АВР

Создание, получение, проверка, XML, NCALayer-подпись, AUTH, отправка и
обновление статуса используют прежние API и провайдеры. AUTH-ticket flow
выделен в общий frontend helper для настроек ЭСФ и карточки АВР.
PIN и приватный ключ не передаются серверу.

В карточке АВР нет отдельной кнопки подключения. «Подписать и отправить АВР»
сохраняет/проверяет документ, проверяет доступность NCALayer, переиспользует
активную сессию ИС ЭСФ либо выполняет прежнюю авторизацию, затем вызывает
прежнюю подпись и отправку. «Проверить документ» проверяет поля без обращения
к NCALayer. При ESF_ENV=off запрос AUTH-тикета не выполняется: пользователь
получает сообщение, что подключение на сервере выключено. Настройки окружения
и разрешение реальной отправки не меняются этим действием.

В карточке сделки результат отправки АВР и ЭСФ остаётся рядом с кнопкой:
проверка, подключение, ожидание подписи, ожидание ответа, затем подтверждение
с внешним идентификатором, регистрационным номером и статусом либо ошибка.
Перед подписью выполняется проверка документа, поэтому отдельное нажатие
«Проверить» не требуется. Внешний идентификатор не подменяет регистрационный
номер; если номер ещё не получен, предлагается обновить статус. Подтверждение
из сохранённого документа отображается и после перезагрузки страницы.
Mock/TEST явно помечены как тестовая отправка. При потере ответа после начала
отправки CRM перечитывает документ; если подтверждения всё ещё нет, показывает
неопределённый результат и блокирует повторное нажатие. Серверные ограничения
повторной отправки остаются в силе.

`DRAFT` отображается как «Черновик», `VALIDATED` как «Готов».
«Подписание» — состояние текущего действия браузера; `SENDING` сохраняется
сервером перед отправкой. `SENT`/`ACCEPTED` и внешний ID поступают из
прежнего провайдера. Наличие `errorCode` отображается как «Ошибка», без
изменения enum модели. Отдельное вычисляемое состояние документов доступно
в карточке сделки и не изменяет воронку.

Создание сериализуется в транзакции; отправка блокирует повтор для того же
документа и другого АВР/ЭСФ того же типа по сделке. Сохранение принимает
`updatedAt` для обнаружения конфликтов. Подготовленные XML-версии АВР
имеют отдельные имена по SHA-256; изменение черновика сбрасывает старый XML.
Отправленные документы не редактируются. Если результат сетевой отправки
неизвестен, автоматический повтор блокируется: нужно сверить результат
с кабинетом ИС ЭСФ, чтобы избежать дубля.

Реестр содержит связь со сделкой, дату, сумму, заказчика, статус,
состояние ЭСФ и ответственного. В «Ситуацию» добавлен счётчик сделок,
требующих закрытия документов, с учётом текущей области ответственного.

## Проверка

Полный набор: `npm run test --workspace=@creolab/api` — 69/69 файлов.
Проверки типов API/web и сборка web проходят.

`avrWorkflow.test.ts` покрывает выбор и готовность, автозаполнение,
конкурентное создание, редактирование/повторное открытие, конфликт версий,
изоляцию организаций, сохранение реквизитов, отсутствие позиций/суммы,
неподписанный договор, отказ mock-ЭСФ, отправку, дубли и реестр.
`avrEditor.test.ts` проверяет точную арифметику и ограничения ввода.
Тесты транспорта NCALayer проверяют отсутствие приложения, отмену и
неверный PIN; прежние тесты AUTH/SOAP/ЭСФ сохранены.

Дополнительно пройден браузерный сценарий на отдельной локальной базе:
выбор → правка → черновик → повторное открытие → подключение → отмена /
неверный PIN → отправка → реестр. NCALayer имитировался, ESF_PROVIDER=mock,
реальная отправка отключена. Проверены desktop и мобильная ширина 390 px.
Проверка с реальным сертификатом и публикация на Render не выполнялись.
