# Развёртывание

## Состав

- `apps/api` — REST
- `apps/worker` — outbox и расписание из PostgreSQL
- `apps/web` — кабинет
- PostgreSQL 16
- Redis (опционально; без него worker polling жив)
- Локальные файлы или S3

`docker-compose.yml` описывает postgres, redis, api, worker. На машине разработки Docker не установлен — compose не прогонялся.

API и worker собираются из `apps/api/Dockerfile`: целевой образ API — `api` (по умолчанию), worker — `worker`. Оба включают рабочие зависимости, LibreOffice и распознавание речи. Worker запускается непосредственно через Node; `tsx` в рабочем образе не нужен. При одновременной работе API и worker события outbox захватываются атомарно, захват продлевается на время обработки и освобождается по таймауту после остановки процесса.

Compose предназначен для проверки на отдельной машине, а не для готового production-развёртывания: пароли БД в примере демонстрационные. Перед запуском нужен `.env` с независимыми рабочими секретами (`SESSION_SECRET`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `ENCRYPTION_KEY`) согласно `.env.example`; они передаются обоим процессам. Не копируйте рабочие ключи и подключения ради локальной проверки. Файлы документов и вложения API/worker хранят в общем постоянном томе `crm_files`. Для отдельного worker на хостинге также нужен доступ к тем же файлам или общему S3-хранилищу.

## Переменные

См. `.env.example`. Бизнес-настройки компаний — в БД. Нет `OWNER_PHONE` для маршрутизации CRM.

## Миграции

Перед обновлением сохранить резервную копию PostgreSQL и файлов. При запуске API/worker обязательные дополнительные изменения применяются транзакционно с advisory-lock; ошибка останавливает запуск. Версия и контрольная сумма миграции биллинга записываются в `BasqarSchemaMigration`.

Для **новой пустой** PostgreSQL-базы сначала применить базовую схему:

```bash
npm run db:generate
# DATABASE_URL задаётся через окружение; команда только для пустой базы.
npx prisma db execute --schema packages/db/prisma/schema.prisma --file packages/db/prisma/init.sql
```

Затем запустить API: он применит обязательные дополнительные миграции. Для существующей базы повторно загружать `init.sql` не нужно. `prisma db push` не заменяет этот порядок: создание актуальных колонок до версионной миграции биллинга мешает её выполнению.

`db:seed` предназначен для демонстрационных и изолированных тестовых баз: он создаёт демонстрационных пользователей и обновляет их пароли. Для рабочего сервиса администратор создаётся штатным bootstrap при запуске API, без seed.

## Приёмка Linux и PostgreSQL перед релизом

Workflow `.github/workflows/release-acceptance.yml` проверяет ветки `codex/stage8-release`, `codex/stage9-release` и `main` на Ubuntu 24.04:

- PostgreSQL 16: отдельная новая база для каждого сценария, базовая схема и настоящие миграции при запуске. Проверяются регистрация → заявка → сделка → счёт → оплаты → отчёт, изоляция компаний и права сотрудников.
- Четыре независимых процесса одновременно запускают миграции и захватывают одно событие очереди. Резервная копия тестовой базы восстанавливается через `pg_dump`/`psql` в другую пустую базу.
- Полный `apps/api/Dockerfile`: сборка модели речи, рабочие зависимости, web и проверка DOC/DOCX → PDF. Из готового образа одновременно запускаются API и worker с `NODE_ENV=production`; проверяются `/health`, `/ready` и опубликованные JS-ресурсы кабинета.

Команда для отдельного одноразового локального PostgreSQL-сервера:

```bash
# BASQAR_TEST_POSTGRES_URL: loopback-сервер, база /postgres, тестовые учётные данные.
node scripts/test-api.mjs --postgres controlForecast salesForecast websiteForms workspaceAcceptance outboxLease schemaPatches financialReporting analyticsPeriods situationSweepMigration postgresRuntime.postgres http
```

Runner не берёт рабочий `DATABASE_URL` для подключения: требует отдельный `BASQAR_TEST_POSTGRES_URL`, создаёт базы `basqar_test_<случайный_id>_<номер>` и удаляет только созданные им базы. Внешние провайдеры отключены. Обычный `node scripts/test-api.mjs` по-прежнему использует изолированные PGlite-базы. Успех CI не заменяет проверку рабочего сайта после деплоя и восстановление его реальных файлов из резервной копии.

## Health

- `GET /health` — процесс жив; `revision` содержит SHA коммита из `RENDER_GIT_COMMIT`, либо `null` вне этого окружения. После деплоя сверить его с опубликованным коммитом.
- `GET /ready` — БД отвечает

Оба ответа имеют `Cache-Control: no-store`, чтобы проверка не подтверждала закэшированное состояние предыдущего деплоя.

## Word на Render

Ошибка `word_conversion_unavailable` означает, что API не смог запустить `soffice` (LibreOffice). Наличие Dockerfile не помогает сервису с runtime Node: Render не использует его при такой настройке.

В `render.yaml` выбран runtime Docker с контекстом корня репозитория и `apps/api/Dockerfile`. Образ устанавливает LibreOffice, собирает кабинет и выполняет `scripts/check-word-runtime.mjs`: оба тестовых договора DOCX/DOC должны преобразоваться в PDF, иначе сборка завершится ошибкой. API использует `API_PORT`, затем выданный Render `PORT`, затем 4100.

Для уже работающего сервиса:

1. Опубликовать изменения репозитория.
2. Если сервис управляется Blueprint — синхронизировать его. Если настройки заданы вручную — в том же сервисе открыть Settings → Build → Source → Edit, сохранить текущие репозиторий и ветку, выбрать Docker, путь `./apps/api/Dockerfile`, контекст `.`. Удалить старое переопределение команды запуска, чтобы применялся CMD образа.
3. Сохранить существующие переменные окружения, подключение БД, домен и постоянный диск `/var/data`. Не создавать заменяющий сервис и не запускать seed для исправления конвертации. Если задан `CRM_SOFFICE_PATH`, он должен указывать на `/usr/bin/soffice` в образе, либо его нужно убрать.
4. Запустить Deploy, убедиться в строках `Word runtime: DOCX → PDF OK` и `Word runtime: DOC → PDF OK`, проверить `/health` и `/ready`, затем импортировать договор через кабинет и проверить оригинал и PDF-копию.

Смена runtime существующего сервиса описана в [документации Render](https://render.com/docs/native-runtimes#changing-a-services-runtime). Локальная успешная проверка не подтверждает установку LibreOffice на действующем сервере.
