# Память при распознавании PDF

Распознавание сначала извлекает готовый текст страницы. Если текстовый слой
содержит меньше 40 символов, запускается OCR. Исходный загруженный файл
не изменяется.

## Обработка сканов

- Первый проход: масштаб до 1,7, длинная сторона до 1800 пикселей,
  площадь до 2 млн пикселей.
- При коротком или неуверенном результате выполняется один повтор:
  масштаб до 2,6, длинная сторона до 2600 пикселей, площадь до 4 млн пикселей.
  Учитывается также уверенность в числах и отдельных словах.
- Если первый проход вернул меньше 40 символов, повтор использует локальный
  адаптивный порог внутри OCR для бледного текста. Для плотного текста остаётся
  обычный порог: адаптивный вариант на проверочном договоре терял строку таблицы.
  Входное изображение остаётся серым,
  с 256 оттенками; необратимая бинаризация исходного файла не выполняется.
- Результат повтора не заменяет первый, если потеряна значительная часть текста
  или уверенность снизилась без существенного увеличения объёма текста.
- В OCR передаётся несжатый PGM, один байт на пиксель. Преобразование из RGBA
  идёт полосами по 32 строки. Цветной холст освобождается до запуска OCR.
- Между страницами очищаются ресурсы PDF, кэш canvas и изображение OCR.
  Языковой движок переиспользуется в пределах документа, затем его поток
  завершается до освобождения слота обработки.
- Используются поставляемые вместе с пакетами модели `4.0.0_best_int`,
  соответствующие LSTM-only движку. Скачивания во время запроса нет.
- На процесс API разрешён один импорт. Следующий запрос получает 429
  `pdf_import_busy`; автоматической очереди нет. При нескольких экземплярах
  API лимит действует отдельно в каждом экземпляре.

## Запуск и проверки

Использовать Node.js 22.18+ и `npm run start --workspace=@creolab/api`.
Production-запуск использует встроенное удаление типов Node, без дополнительной
обработки больших PDF-модулей через tsx. Команда разработки продолжает
использовать tsx и может потреблять больше памяти.

Локальный замер шестистраничного договора на macOS, Node 22.23.2:

| Вариант | Пиковая RSS | Время |
| --- | ---: | ---: |
| Исходная обработка с tsx | 752 МиБ | 21,6 с |
| Оптимизированная обработка с production-способом запуска, итоговый замер | 576 МиБ | 26,6 с |

Это память отдельного проверочного процесса, а не всего сервиса CRM.
Снижение примерно 23% включает изменения изображений, языковых моделей
и способа запуска. Оно не является замером только эффекта уменьшения картинок.
Номер, дата, телефон, БИН, IBAN, БИК, количества, цены трёх позиций и итог
совпали с предыдущим результатом. Это регрессия относительно старого OCR,
а не гарантия правильности каждого символа исходного договора.

До последней корректировки обработки бледного текста пройдены 64/64 набора
тестов API/контрактов, проверка типов и сборка веб-интерфейса. После корректировки
повторно проверены OCR и разбор реального договора. Также ограничено определение
колонок реквизитов заголовками начала раздела, чтобы подписи внизу страницы
не смешивали стороны договора.
Отдельные проверки покрывают серые оттенки, прозрачность, пределы разрешения,
выбор повторного OCR, бледный/цветной скан между текстовыми страницами,
ограничение параллельной загрузки и освобождение слота после ошибки.

## Ограничения

576 МиБ всё ещё превышают 512 МиБ, причём остальной CRM тоже нужна память.
Эти изменения сами по себе не подтверждают исправление 502 на сервере
с таким лимитом. Нужен замер полного процесса на целевом Linux-сервере,
включая повторные загрузки, и сверка журналов хостинга. Публикация и изменение
тарифа в рамках этой проверки не выполнялись.

Распознавание пока выполняется внутри HTTP-запроса. Повторный проход повышает
точность ценой времени; для длинных сканов остаётся риск ограничения времени
со стороны хостинга. Проверка полей пользователем перед сохранением обязательна.
