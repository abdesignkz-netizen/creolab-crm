# Исправление передачи подписи NCALayer — 24.09.2026

При подписании DOG-2026-0011 после выбора ЭЦП ТОО пользователь получил
«Подпись не прошла проверку». Проверка рабочего API показала: версия договора
зафиксирована, запрос исполнителя PENDING, сохранённых подписей нет. БИН запроса
совпадает с юридическим профилем компании. Неуспешная CMS предыдущей попытки не
сохранялась, поэтому её индивидуальный ответ верификатора недоступен.

Воспроизведена ошибка на корректной синтетической подписи: контейнер с оболочкой
`-----BEGIN CMS-----` проходил разбор сертификата, но передавался в Kalkan без
удаления оболочки. Java принимает в этом поле Base64 бинарного CMS, поэтому
возвращала `cms_verify_failed`. Формат PEM ответа NCALayer описан в
[разборе НУЦ](https://forum.pki.gov.kz/t/vopros-po-kz-gov-pki-knca-basics/2205).

Теперь передача в Kalkan и сохранение подписи используют тот же декодер, что и
разбор сертификата. Меняется только транспортная оболочка; байты CMS и договора
сохраняются. Криптография, срок действия, БИН/ИИН и доверие сертификату проверяются
как прежде. Ошибки сертификата получили понятные сообщения. В карточке пояснена
возможность повторить подписание зафиксированной версии после неудачной попытки.

Проверки:

- До исправления тест корректного PEM возвращал FAILED / cms_verify_failed.
- После исправления: cmsInspect и documentsPhase3, 17 тестов, без ошибок.
  Полный путь исполнителя и заказчика проверен с PEM, включая параллельную отправку,
  отказ для другого файла и БИН, неизменность договора при отказе.
- Реальный локальный Kalkan SDK 0.7.2: RSA и ГОСТ-2015 принимают исходные байты,
  отклоняют другой файл и attached CMS. API-клиент передал PEM ГОСТ через Java HTTP
  и получил VERIFIED по криптографии; CRM отклонила недоверенный тестовый сертификат.
- Проверка типов API и web, сборка web, git diff --check прошли.

В проверках использованы синтетические ключи. Реальный договор не подписывался
автоматически; окончательную проверку с ЭЦП компании выполняет владелец в NCALayer.
